# CLAUDE.md — SPX Vendor Price Portal

Instructions for Claude Code working in this repo. Read this file fully before changing anything.

## What this system does

SPX TH collects monthly manpower bid prices from external vendors and tracks them.

```
Vendor ──► docs/index.html (GitHub Pages, public)
              │  sign-in: company name + access code (checked against hashes in docs/config.js)
              │  one POST per price line ─────────────────────────────┐
              ▼                                                       ▼
        hidden Google Form ──► "Form Responses" tab in the VENDOR SUBMISSION Google Sheet (private, company account)
                                      │  Tracker_Sync.gs pulls daily 18:00 Bangkok + "Retrieve now"
                                      │  re-checks name + code, rejects bad rows, splits each line into
                                      ▼  "Without shift" and "With shift" price rows
                         TRACKER Google Sheet: Database → Tracker / Trend tabs (formulas)
```

Why this design: the company Google Workspace blocks Apps Script web apps for outside users, so the page is
hosted on GitHub Pages and saves through a Google Form instead. Vendors never get access to any spreadsheet.

## Hard rules

1. **Never commit vendor data.** No prices, vendor names with codes, spreadsheets, CSV exports or screenshots of them.
   `.gitignore` blocks `*.xlsx` / `*.csv` — do not override it.
2. **`docs/config.js` is public.** It may only contain the keys the tests allow; access codes appear **only as hashes**.
   Never add vendor names, codes, prices, target prices or spreadsheet IDs to anything under `docs/`.
3. **Never edit `docs/config.js` by hand** except to replace it with a file generated by *Web Form → 2) Build web page*.
4. **Keep `docs/index.html` and `apps-script/vendor-sheet/WebPage.html` identical** apart from the
   `<script src="config.js"></script>` line. Edit one, copy to the other, run tests.
5. **Target prices are internal.** They live only in the tracker's Lists tab. Never send them to the vendor page.
6. Run `npm test` before every commit. Do not push to `main` with failing tests.
7. Apps Script files are deployed **by pasting into the Apps Script editor** (or `clasp`, if the user has set it up).
   After changing a `.gs`/`.html` file under `apps-script/`, always tell the user exactly which file to paste
   into which project, and whether a redeploy / rebuild is needed (see "After a change").

## Contracts that must stay in sync

Breaking any of these silently loses vendor submissions. The tests in `tests/` guard them.

**1. Access-code hash** — `vendorHash()` in the page, `webHash_()` in `Backend_Setup.gs`:
`SHA-256( salt + "|" + norm(name) + "|" + lower(trim(code)) )`, then re-hash the raw 32 bytes, `ITERATIONS` times total
(2000), lowercase hex. `norm()` = lowercase, remove everything except `a-z 0-9` and Thai letters `\u0E00-\u0E7F`.
The same `norm` rule is `normName_()` in `Tracker_Sync.gs`. Changing `ITERATIONS`, the salt format or `norm`
requires changing all three **and** rebuilding `config.js`.

**2. Form question titles** — `WEB_FIELDS` in `Backend_Setup.gs` ↔ `vals` keys in `sendLines()` (page) ↔
`need` list in `collectFormLines_()` (tracker):

| Page key | Form question title |
|---|---|
| vendor | Vendor Name |
| code | Access Code |
| facility | Facility |
| nationality | Nationality (`TH` / `BM`) |
| scheme | Working Scheme (`8hr` / `10hr`) |
| type | Price Type (`BAU` / `Campaign`) |
| price | Price without shift |
| priceShift | Price with shift |
| bauHc | Max BAU HC (required, whole number ≥ 0) |
| campHc | Max Campaign HC (required, whole number ≥ 0) |
| remark | Remark (optional) |
| ref | Submission Ref |

Plus `Timestamp` (added by Google) and `Imported At` (added by the setup / tracker). Never rename questions in the
Google Form UI.

**3. Legacy web app `Submissions` tab** (A–M): ID, Timestamp, Vendor, Facility, Price Type, Price without shift,
Max BAU HC, Max Campaign HC, Remark, **Imported At (J)**, Nationality, Working Scheme, Price with shift.

**4. Tracker `Database` tab** — `Tracker_Sync.gs` writes columns **C:M** starting row 6 (formula rows end at 1005):
Date, Vendor, Facility, Nationality, Scheme, **Shift**, Price Type, Price, BAU HC, Campaign HC, Remark.
Column U = Combo Key (used by `healthCheck_`). Lists tab: vendors `B6:B25`, facilities `D6:D35`,
targets `E6:T35`, months `V6:V29`, first month `X6`. These are hard-coded in `CFG` at the top of `Tracker_Sync.gs`.

**5. Facility names** are plain site names (`SOCN`, not `SOCN (BM)`); nationality is its own field.

## Commands

```bash
npm test          # all contract + syntax tests (Node 20+, no dependencies)
npm run serve     # preview the page at http://localhost:8080 (uses docs/config.js)
```

With the placeholder `config.js` the page loads but sign-in always fails and Submit says "Preview only".
To preview sign-in locally, temporarily use a real generated `config.js` — do not commit test configs.

## Common tasks

### A. First-time setup (GitHub)
1. Confirm with the user the repo name and that it may be **public** (GitHub Pages for outside vendors needs a public
   site; company org policy may restrict public repos — ask if unsure).
2. ```bash
   git init && git add . && git commit -m "Vendor price portal"
   gh repo create <name> --public --source . --push
   gh api -X POST "repos/{owner}/<name>/pages" -f build_type=workflow   # Pages source = GitHub Actions
   ```
3. Watch the run: `gh run watch`. The page URL is `https://<owner>.github.io/<name>/`.
4. Tell the user to do the Google side (they must do this themselves — Claude Code cannot open their sheets):
   vendor sheet → Extensions → Apps Script → add `Backend_Setup.gs` (script) and `WebPage` (HTML) → save →
   reload → **Web Form → 1) Create form backend** → test the form link in an incognito window (must open without a
   company login) → fill access codes (≥ 12 chars) in the Vendors tab → **Web Form → 2) Build web page** →
   download `config.js` from Drive. Then continue with task B.

### B. Publish a new `config.js` (after codes, vendors or facilities change) — most common task
1. The user downloads `config.js` from Drive (generated by *Web Form → 2) Build web page*) and gives you its path.
2. Copy it to `docs/config.js` (replace the whole file).
3. `npm test` — the "real build" test must now run (not skip) and pass. If a test fails, stop and explain; do not
   "fix" the config by hand.
4. Commit `Update vendor config (<builtAt value>)` and push to `main`. Check `gh run watch` until deploy succeeds.
5. Remind the user: vendors may need a hard refresh (Ctrl+F5) to get the new codes.

### C. Change the page (text, layout, validation)
1. Edit `docs/index.html`, then copy the same change into `apps-script/vendor-sheet/WebPage.html`
   (only difference allowed: the `config.js` script tag).
2. Keep labels bilingual (English / Thai). Keep all fields required except Remark. Keep it mobile-friendly.
3. `npm test`, `npm run serve` to check visually, commit, push.
4. No Apps Script change needed unless the field contract changed.

### D. Add / rename / remove a submission field (touches everything)
1. `Backend_Setup.gs` → `WEB_FIELDS` (new key + question title).
2. Page (`docs/index.html` + `WebPage.html`) → template input, `collect()`, required-field check, `sendLines()` `vals`,
   receipt table.
3. `Tracker_Sync.gs` → `need` list and `collectFormLines_()` mapping; if it reaches the Database, also `toRows_()`
   and the tracker workbook columns (tell the user — the workbook is not in this repo).
4. `npm test` (field-contract test must pass).
5. Tell the user the Google steps in this order: paste updated `Backend_Setup.gs` → the existing form does **not** get
   new questions automatically: add the question in the form with the **exact** title, at the end → **Build web page**
   again → give you the new `config.js` (task B) → paste updated `Tracker_Sync.gs` into the tracker project.

### E. Change Apps Script code
Edit the file under `apps-script/`, run `npm test`, commit. Then tell the user precisely:

| Changed file | Paste into | Then |
|---|---|---|
| `vendor-sheet/Backend_Setup.gs` | Vendor sheet project, file `Backend_Setup` | Reload sheet; rebuild page if config logic changed |
| `vendor-sheet/WebPage.html` | Vendor sheet project, HTML file `WebPage` | Only matters for the all-in-one build |
| `vendor-sheet/legacy-webapp/*` | Vendor sheet project, `Code` / `Form` | Deploy → Manage deployments → Edit → **New version** |
| `tracker/Tracker_Sync.gs` | Tracker sheet project | Save. Re-run *Set up daily sync* only if triggers changed |

Optional `clasp` (only if the user asks and their admin allows the Apps Script API): one folder per project,
`.clasp.json` with the scriptId — `.clasp.json` is git-ignored, never commit it.

## Troubleshooting

| Symptom | Likely cause | Action |
|---|---|---|
| Vendor: "Company name or access code is not correct" | Code changed but `config.js` not republished; typo; vendor has no code | Task B; check Vendors tab |
| Vendor sees old facility list | Old `config.js` cached / not rebuilt | Rebuild + task B; hard refresh |
| Rows in Form Responses but not in tracker | Sync not run, or stamped `REJECTED – …` in *Imported At* | Check Sync tab log; fix Vendors/Facilities; clear the cell to retry |
| Nothing reaches Form Responses | Form restricted to company users, or form questions renamed | Form → Settings → Responses → allow outside; never rename questions |
| CI fails on `config.test.mjs` | `config.js` hand-edited or from a different build | Regenerate via Build web page |
| CI fails on `hash-contract` | Hash or `norm` edited in one place only | Make all three identical (contract 1) |
| Tracker/Trend not showing new rows | Filters (Shift etc.), name not in Lists, month past `V29`, Row Check = Incomplete | See Sync log ⚠ warnings |

## Limits to remember
- The page posts with `mode: 'no-cors'`; it cannot read Google's reply. "Submitted" means *sent*. Confirmation is the
  row in Form Responses.
- Hashes in a public file can be brute-forced offline if codes are short — keep codes ≥ 12 random characters.
  The tracker re-checks every row, so a guessed code is the only way in; rotate a vendor's code if it leaks.
- Revisions are not flagged on the page; the tracker Database marks repeats as `Duplicate` (lowest price used).
